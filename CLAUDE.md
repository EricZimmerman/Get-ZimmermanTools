# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Two PowerShell scripts:

- **`Get-ZimmermanTools.ps1`** (for users; ships as `Get-ZimmermanTools.zip`): finds every download on https://tools.ericzimmermanstools.com and downloads what changed (by SHA-1, kept in a CSV) to `-Dest`: .NET Framework zips from the site's top level, .NET 10 ones from `/net/` into `<Dest>\net` (`-NetVersion 0|4|10`, default 10; 9 maps to 10 with a warning). First it checks for a newer version of itself (`Update-Self`: downloads `Get-ZimmermanTools.zip`, compares its script with the running one ignoring the signature block and line endings, and if they differ extracts it over the running script (and a renamed copy) and stops, telling the user to run it again; skipped with `-NoUpdate`, when not run from a file, or when the script's folder has a `.git` so a working copy is never replaced; a failed check warns and carries on). Must keep working in Windows PowerShell 5.1 and PowerShell 7.
- **`Build-ZimmermanTools.ps1`** (for the maintainer; not in the user zip): builds every EZ Tools program from its repository, cloned next to this one (`-Root`, default the parent folder), stages each as its download zip is laid out (`-Out`), signs (`-Sign`), and makes the zips (`-Zip`: .NET Framework at the top, .NET 10 in `net\`). The frameworks come from each project's TargetFramework(s), so a program that drops one (Hasher, AmcacheParser and XWFIM are .NET 10 only) is no longer built or zipped for it; `-Zip` then warns about the old zip still in the destination (it doesn't delete it: the destination is often the download share). `-Tool a,b` (`-Only`) builds a few, `-Clear` empties `-Out` first (never a drive, a repository or the repositories' folder). GNU style switches (`--out`, `--tool`, ...) work too. `Get-Help .\Build-ZimmermanTools.ps1 -Full` has the rest.

## Build-ZimmermanTools: how it works

- **The program table** (`$programs`) is the description of every download zip: `Project`, `Folder` (the folder in the zip), `Files` (from the build besides the defaults), `Copy` (repository folders or files: EvtxECmd and SQLECmd maps, RECmd batch files, Registry Explorer bookmarks and manual, each GUI's `LICENSE.txt` from its repository root (Eric, 2026-10-22)), `Release` (files only in the current release zips, downloaded once into `%TEMP%\Build-ZimmermanTools\_release`: GeoLite2-City.mmdb, XWFIM's text files, Registry Explorer's default settings), `Special` (the registry and TLE plugins, built with each repository's `CopyPlugins.ps1 -Build`; TLE's layouts come from TLEFilePlugins `Layouts\Default`, their source of truth), `Natives` (native libraries from the build output, `path in the build` -> `path in the staged program`, staged as files next to the tool: AmcacheParser and WxTCmd's `e_sqlite3.dll`/`libe_sqlite3.so`/`libe_sqlite3.dylib` (win-x64, linux-x64, osx-arm64, from `runtimes\<rid>\native`, flat next to the tool: each OS has its own name, and .NET looks in the app folder first), SQLECmd's four `runtimes\<rid>\native\SQLite.Interop.dll` (same name on every OS: NativeSqlite.cs loads that path)). A tool whose output or content changes needs its entry changed here.
- **Costura**: the command line tools (net4 and .NET 10) keep it: their dependencies are inside the exe/dll, so they stage as `{0}.exe`, `{0}.dll`, `{0}.runtimeconfig.json` and can sit side by side in one folder. Costura does not embed native libraries (SQLite) here, and nothing may be extracted on the user's machine when a tool runs (Eric, 2026-10-20: "not put anything outside the directories or on someone's machine"): they are the table's `Natives`, files next to the tool; staging fails if the tool's dll has a native library inside (`Get-EmbeddedNatives`: Costura's `costura32.`/`costura64.`/`costura-<rid>.` unmanaged resources, or SQLite.Interop/e_sqlite3 embedded by hand as SQLECmd once did). The command line tools stay cross platform (Eric, 2026-10-20: "single exe should be for the GUIs only"; `dotnet <Tool>.dll` on any OS): never publish them as single files. The programs with a window have no Costura (Eric, 2026-10-20: without it they start 2.5-5x faster and use about half the memory, as Defender scans the assemblies Costura unpacks in memory) and are each **one exe** (round 4, Eric 2026-10-20): `Test-SingleFileGui` (a `Gui`, .NET, not net4; TimeApp too, its `TimeApp.exe` at the top of its zip as it has no Folder) publishes them with `dotnet publish -c Release -f <tfm> -r win-x64 --self-contained false -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=false` (given on the command line, so the release doesn't depend on the project file) and stages the publish output as it is, without pdbs (no release zip ever had any): the exe with every managed dependency inside, and next to it the native dlls if any (never extracted to `%TEMP%\.net`, nothing is written outside the program's folder; the GUIs exclude DevExpress' unused `sni.dll` in their projects), content files (EZViewer's Extensions.yaml), plus the table's Copy/Release/Special. Each GUI is in its own folder in its zip (`net\RegistryExplorer\...`), so `Get-ZimmermanTools.ps1`, which extracts every zip into the same `net\` folder, never mixes their files (TimeApp, at the top, is only `TimeApp.exe`). No GUI generates binding redirects (`AutoGenerateBindingRedirects`, .NET Framework only): and no GUI has an App.config (Eric, 2026-10-20: Registry Explorer's DirectX setting is in code), so none ships a `{0}.dll.config`. A GUI project that still has Costura, or needs Visual Studio's MSBuild (licenses.licx for it), fails. **ezTriage is not in the table and must not be added** (Eric, 2026-10-20): it has its own release script, `Build-Release.ps1` in the ezTriage repository.
- **Content comes from the local clones**, not GitHub; the maintainer keeps them in sync with the remotes. The tools' own `--sync` downloads the same folders from GitHub `master` and compares bytes, so the `Copy` folders and TLE's layouts are taken as committed at HEAD (`Export-RepoPath`: `git archive` with `core.autocrlf=false`), not from the working copy, whose CRLF made `--sync` report every map as updated. Uncommitted changes there are left out with a warning. The script itself (`Get-ZimmermanTools.ps1`) stays the working copy's CRLF, as released before.
- **Builds**: the GUIs: `dotnet publish` as above into `%TEMP%\Build-ZimmermanTools\_build\<Program>\<fw>`; the command line tools (AmcacheParser and WxTCmd too, since 2026-10-20: Costura, natives next to them, instead of single files that extracted SQLite to `%TEMP%\.net`): `dotnet build -f <tfm> -o %TEMP%\Build-ZimmermanTools\_build\<Program>\<fw> --no-incremental` (local, never in `-Out`, which is often a share; `--clear` empties it too) (full builds: an incremental build skipped Costura weaving once). Visual Studio's MSBuild only for old-style projects or a `licenses.licx` embedded for any MSBuild; MSBuild 18 ends with 0x4000001E when given `OutDir`/`TargetFramework` or with dotnet build server nodes left, so the script restores and builds separately and shuts the nodes down.
- **Checks**: every dll the build made must be staged (anywhere in the program) or embedded by Costura (read from the assembly's metadata) or in a single file's bundle; a Costura program with nothing embedded fails. For a GUI (single file), `Get-BundleManifest` reads the exe's bundle manifest (the header offset sits before a fixed 32-byte signature in the host; then each bundled file's path and type, and the bundled deps.json): chosen over comparing with a second, normal build because it is what the shipped exe really contains and costs no extra build. The exe must be a bundle with a deps.json; every file that deps.json lists (`Get-DepsAssets -Text`) must be in the bundle or staged next to the exe; no managed dll may be loose in the program outside `Plugins\` (it belongs in the exe); every file the publish made but pdbs must be staged, those next to the exe as published (same size; in subfolders the table's Special may replace them: Timeline Explorer's project copies its plugins and the working copy's layouts into the publish, Special stages the plugins CopyPlugins built and the layouts as committed). **Zips sharing a folder**: `Get-ZimmermanTools.ps1` extracts every .NET 10 zip into one `net\` folder (and the .NET Framework ones and the script at the top), so two zips with a file at the same path overwrite each other; that is allowed only for identical bytes (AmcacheParser and WxTCmd both have the three e_sqlite3 libraries at the top: the same SQLitePCLRaw version in both repositories). `Get-SharedPathConflicts` hashes every such path across all programs staged in `-Out` (also those from an earlier `--only` run); staging adds a FAILED row for each difference, and `--zip` refuses to zip anything. **Pdbs** (round 6, Eric 2026-10-20: every repository has `DebugType embedded` and Release `ContinuousIntegrationBuild` in its `Directory.Build.props`): staging never stages a `.pdb` (the GUIs' publish output is copied without them; the tools stage only their named files) and fails a program if one ends up staged anyway; `Get-EmbeddedPdbInfo` reads the program's own assembly (a tool's `{0}.dll`, net4 `{0}.exe`; a single file's `{0}.dll` from its bundle, `Get-BundleFileBytes`, inflated if the bundle is compressed) and **fails** the program if it has no embedded pdb or has source paths under this machine's folders (`-Root`, the user profile, `%TEMP%`; other non-`/_/` paths are not this machine's: Costura adds its template's sources as `C:\CI_WS\...` from Fody's build, VB an unnamed document). It was a warning until a clean full staging run had none (Eric, 2026-10-22). Failures are listed in the summary table and set the exit code.
- **The script**: the `Get-ZimmermanTools` entry (`Script`) copies `Get-ZimmermanTools.ps1` into `<Out>\Get-ZimmermanTools\script`; `--sign` signs that copy (the repository's stays unsigned) and `--zip` makes `Get-ZimmermanTools.zip` at the top.
- **Two machines**: Eric stages on the dev machine and signs on another (hardware token). Staging copies this script and writes `_staged.txt` at the top of `-Out`; that copy, run with `--sign --zip <dir>` and no `--out`/`--staged`, takes its own folder as the staged one. Sign and zip must keep working without repositories and in Windows PowerShell 5.1 (no `$PSScriptRoot` in param defaults, no `File.Move` overwrite, `[NullString]::Value` for a null string argument).
- **Signing**: only Eric's files (Eric, 2026-10-20: not Microsoft's, DevExpress' or other third-party DLLs). Staging decides, since the signing machine has no build output or NuGet cache: `Get-SignEntries` lists every `.exe` and `.ps1` of a staged program (a GUI's single-file exe is signed whole: signtool signs a bundle like any PE, the bundle stays readable since its offset is inside the host and the signature is appended after it), its own `{0}.dll`, the plugin DLLs (`Special`), and (a command line tool's build; a GUI's single file has its own inside) the DLLs of deps.json `"type": "project"` libraries or of packages whose `.nuspec` in the NuGet cache names Zimmerman (authors/owners/copyright) or a github.com/EricZimmerman URL (`Test-EricPackage`; a hard-coded id list only when the `.nuspec` is missing); `Test-VendorFile` (name prefix, a version-info company starting with Microsoft/DevExpress/Developer Express, or a Microsoft Corporation/Developer Express copyright: not "Microsoft" anywhere, TLEFileMicrosoft has its own name as company) always excludes Microsoft's and DevExpress'. The list is `<Out>\_sign.txt` (`#` header, one path per line relative to `-Out`; an `--only` run keeps the other programs' lines while their files exist). `--sign` signs only listed files (a missing one is an error, a program folder with no line a warning, the other files counted as left unsigned by design); without `_sign.txt` it stops (restage) instead of signing everything. `--zip` zips each program/framework folder, so files at the top (`_sign.txt`, `_staged.txt`, the script copy) are in no zip. `signtool sign /fd sha256 /tr <timestamp> /td sha256` (`/a`, or `/f` with `-CertFile`), many files per call so a token asks once per call; files already validly signed are skipped unless `-Force` (which still re-signs only listed files, never Microsoft's or DevExpress'). Never run signing on a machine without the user asking: `/a` picks the user's real certificate.
- **Zips** (`--zip`): made locally, copied next to the destination zip as `<name>.zip.partial-<guid>`, then renamed over it (one step, also on a share): a download meanwhile gets the whole old zip. Nothing is deleted at the destination (an old `net9\` folder or a zip no longer made stays).
- Output: each program's `== Program fw` line in red, helper scripts' messages indented under it, then a summary table.

## Testing

No automated tests. Verify a change by staging a few programs to a temp folder (`--out <temp> --tool A,B --clear`) and comparing each staged folder with the current release zip (same files, except intended changes) and with what the build produced. A full run (`--out`) builds everything and takes a while.

## Versioning and release

No version. `Get-ZimmermanTools.ps1` is released by zipping it to the download share (`Get-ZimmermanTools.zip`, the script's `script` entry). The website (`ericzimmerman.github.io`) links to the same URLs: its links and the share's layout must change together.
